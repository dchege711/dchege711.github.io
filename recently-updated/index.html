Oct 24, 2026»Managing Limited Resources 4 min; updated Oct 24, 2026

Limit Concurrent Operations

Applies when you have operations that can run concurrently, but you need to cap how many can run at once, e.g., integrating with an external API that allows at most 10 concurrent requests per account, limiting number of image processing jobs to avoid CPU saturation, etc.

Semaphores solve this directly, e.g.,

public class APIClient
{
  // Limit to at most 5 concurrent requests.
  private readonly SemaphoreSlim _requestPermits = new SemaphoreSlim(5);

  public async Task<Response> MakeRequestAsync(string endpoint)
  {
    await _requestPermits.WaitAsync(); // Block if 5 requests are in-flight

    try { return await _httpClient.GetAsync(endpoint); }
    finally { _requestPermits.Release(); }
  }
}

  {
    _requestCounts.TryGetValue(userId, out int count);

Oct 22, 2026»Coordinating Work Between Threads 5 min; updated Oct 22, 2026

The Problem

Some work should not be ran in the mainline as it takes too long, and makes your mainline unresponsive, e.g., on user signup, sending a welcome email should be done out of line lest your application cannot process new requests. Conceptually, API handlers produce tasks, workers consume tasks, and something sits in between to coordinate the handoff.

Three things need solving in this scenario:

  • Efficient waiting: Consumers should sleep when there’s no work, and wake up immediately when new work arrives.
  • Backpressure: Producers should slow down when consumers can’t keep up, preventing memory exhaustion which would take down the whole application.
  • Thread safety: The coordination mechanism itself must handle concurrent access without corruption.

Sep 17, 2026»Conjunctive Probability 1 min; updated Oct 3, 2026

Definition

Given two propositions, \(A\) and \(B\), the conjunction \(A \cap B\) (read \(A\) and \(B\)) is true if both \(A\) and \(B\) are true, and false otherwise. Conjunction is commutative, i.e., \(\mathbb{P}(A \cap B) = \mathbb{P}(B \cap A)\). 

from __future__ import annotations

import pandas as pd

from .probability_defn import probability


def conjunctive_probability(A: pd.Series[bool], B: pd.Series[bool]) -> float:
    # Given two Boolean series, the `&` operator computes their conjunction.
    return probability(A & B)

Sep 29, 2017»Conditional Probability 1 min; updated Oct 3, 2026

Definition

\( \mathbb{P}(A|B) \) is the probability of event \(A\) given that event \(B\) occurs:

$$ \mathbb{P}(A|B) = \frac{\mathbb{P}(A \cap B)}{\mathbb{P}(B)} $$

Notice that if \(P(B) = 0\) then it’s meaningless to condition \(A\) on \(B\). 

from __future__ import annotations

import pandas as pd

from .probability_defn import probability


def conditional_probability(
    proposition: pd.Series[bool], given: pd.Series[bool]
) -> float:
    # proposition[given] contains the values of proposition for given.
    return probability(proposition[given])

Oct 3, 2026»State Machine 1 min; updated Oct 3, 2026

Motivation

Use it when an object’s behavior changes based on its internal state and you have complex state transition rules. It’s the antidote to scattered conditionals checking current state. Each state know which state comes next and what actions are valid.

Sample Code

public interface IVendingMachineState
{
  void InsertCoin(VendingMachine machine);
  void SelectProduct(VendingMachine machine);
  void Dispense(VendingMachine machine);
}

public class NoCoinState : IVendingMachineState
{
  public void InsertCoin(VendingMachine machine) =>
    machine.SetState(new HasCoinState());

  public void SelectProduct(VendingMachine machine) =>
    Console.WriteLine("Insert coin first");

  public void Dispense(VendingMachine machine) =>
    Console.WriteLine("Insert coin first");
}

public class HasCoinState : IVendingMachineState { ... }

public class DispenseState : IVendingMachineState { ... }

public class VendingMachine
{
  private IVendingMachineState _currentState;

  public VendingMachine() => _currentState = new NoCoinState();

  public SetState(IVendingMachineState state) => _currentState = state;

  public void InsertCoin() => _currentState.InsertCoin(this);
  public void SelectProduct() => _currentState.SelectProduct(this);
  public void Dispense() => _currentState.Dispense(this);
}

Oct 3, 2026»OOP Structural Patterns: Facade 1 min; updated Oct 3, 2026

Definition

A facade is an orchestrator class that hides the complexity of coordinating multiple components behind a clean interface. It’s rare to explicitly name it as most new code design clean orchestrators from scratch. You might name it when wrapping existing messy code, e.g., after inheriting a complex subsystem with awkward APIs.

Sample Code

public enum GameState { InProgress, Won, Draw }

public class Board
{
  public bool PlaceMark(int r, int c, string mark) { ... }
  public bool CheckWin(int r, int c) { ... }
  public bool IsFull() { ... }
}

public class Player
{
  public string Mark { get; }
  public Player(string mark) { ... }
}

public class Game // This is the Facade
{
  private readonly Board _board;
  private readonly Player _playerX;
  private readonly Player _playerO;
  private Player _currentPlayer;
  private GameState _gameState;

  public Game() { ... }

  public bool MakeMove(int r, int c)
  {
    if (_gameState != GameState.InProgress) return false;

    if (!_board.PlaceMark(r, c, _currentPlayer.Mark)) return false;

    if (_board.CheckWin(r, c))
      _gameState = GameState.Won;
    else if (_board.IsFull())
      _gameState = GameState.Draw;
    else
      _currentPlayer = _currentPlayer == playerX ? playerO : playerX;

    return true;
  }
}

Oct 3, 2026»OOP Structural Patterns: Decorator 2 min; updated Oct 3, 2026

Example

public interface IDataSource
{
  void WriteData(string data);
  string ReadData();
}

public class FileDataSource(string fileName) : IDataSource
{
  public void WriteData(string data) { ... }
  public string ReadData() { ... }
}

public class EncryptionDecorator(IDataSource wrapped) : IDataSource
{
  public void WriteData(string data) => wrapped.WriteData(Encrypt(data));
  public string ReadData() => Decrypt(wrapped.ReadData());
  private string Encrypt(string data) { ... }
  private string Decrypt(string data) { ... }
}

… where we can have other decorators, e.g., CompressionDecorator. Usage is of the form:

IDataSource source = new FileDataSource("data.txt");
source = new EncryptionDecorator(source);
source = new CompressionDecorator(source);
source.WriteData("Sensitive info");

Use Case

When you need to layer on extra functionality at runtime based on conditions, e.g., encrypt certain messages, wrap a service with logging in debug mode, etc.

Consider a Window in a windowing system. To allow scrolling on some Window objects, one could either create a ScrollingWindow subclass, or create a ScrollingWindowDecorator that adds this functionality to existing Window objects. Suppose you then want to support adding borders to some Window objects. If continuing with sub-classing, then we’d have WindowWithBorder, ScrollingWindowWithBorder, etc. Compare that to having a BorderedWindowDecorator, where any combination of ScrollingWindowDecorator or BorderedWindowDecorator can decorate existing Windows. If the functionality needs to be added to all Windows, the base class can be modified. However, sometimes modifying the base class is not possible, e.g., using an external framework where it’s not possible/legal to modify the base class.

Overview

Cancellation is cooperative. One part of the code politely notifies the other code that it’d like it to please stop. The responding code may immediately stop, or continue until it reaches a valid stopping point, or ignore the cancellation request entirely.

Most code has the form:

async Task DoSomethingAsync(int data, CancellationToken cancellationToken)
{
  var intermediateValue = await DoFirstStepAsync(data, cancellationToken);
  await DoSecondStepAsync(intermediateValue, cancellationToken);
}

… where the CancellationToken is passed down to whatever APIs you call.
